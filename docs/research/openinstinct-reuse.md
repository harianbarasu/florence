## Bottom line

OpenInstinct is useful to Florence primarily as a **working, source-available Kernel browser operator**: persistent browser profiles, fast in-browser Playwright programs, native visual computer controls, login continuity, user-visible browser images, and native iMessage attachment delivery. Those are concrete product capabilities Florence can take rather than rebuild.

It is not a better general-agent runtime, household memory system, proactive planner, or family product. OpenInstinct describes itself as a personal iMessage browser assistant for chores, tickets, and groceries, and its deployed stack stores per-user memory ([README lines 5-15](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/README.md#L5-L15), [lines 29-32](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/README.md#L29-L32), [lines 62-64](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/README.md#L62-L64)). The repository has no household model, two-parent boundary, recipe or dinner-planning artifact, 90-day source review, reminder scheduler, or proactive docket implementation. Florence should keep its existing household product model and durable PostgreSQL work loop.

The provider recommendation is to **replace Browserbase with Kernel behind Florence's existing browser interface**, initially as a rollout substitution rather than a second runtime or permanent dual-provider framework. OpenInstinct supplies a close TypeScript implementation of the missing operator layer. Browserbase is not incapable: its official Contexts, auth, live-view, upload, download, and screenshot surfaces cover much of the same ground. Kernel wins here because it combines those primitives with first-party in-VM Playwright and OS-level computer controls, and because the exact integration can be adapted from OpenInstinct.

## Kernel versus Browserbase

This comparison is based on the current official provider documentation as well as OpenInstinct's pinned source.

| Product need | Kernel | Browserbase | Decision for Florence |
| --- | --- | --- | --- |
| Persistent signed-in state | Browser creation supports profiles that retain cookies/storage, and Kernel also offers Managed Auth ([browser creation](https://www.kernel.sh/docs/introduction/create), [Managed Auth](https://www.kernel.sh/docs/auth/overview)). OpenInstinct already implements stable workspace profiles and controlled profile writes. | Contexts store auth state, live indefinitely until deletion/invalidation, and can be reused across sessions ([Contexts](https://docs.browserbase.com/platform/browser/core-features/contexts), [authentication](https://docs.browserbase.com/platform/identity/authentication)). Florence's current adapter does not use them. | Capability is available from both. Kernel wins on directly reusable implementation, not because Browserbase cannot persist login. |
| DOM execution | Kernel executes Playwright/TypeScript inside the browser VM, with `page`, `context`, and `browser`, explicitly avoiding CDP overhead ([Playwright execution](https://www.kernel.sh/docs/browsers/playwright-execution)). | Browserbase supports Playwright over a remote session/CDP connection; Florence currently drives an `agent-browser` CLI over CDP. | Kernel's first-party execution primitive is a cleaner way to let one model call inspect, act, and verify. |
| Visual/computer use | Kernel exposes OS-level mouse, keyboard, scroll, drag, clipboard, and optimized screenshots ([computer controls](https://www.kernel.sh/docs/browsers/computer-controls)). | Browserbase provides interactive live view and CDP screenshots ([live view](https://docs.browserbase.com/platform/browser/observability/session-live-view), [screenshots](https://docs.browserbase.com/platform/browser/files/screenshots)); computer-use is possible through surrounding integrations, but OpenInstinct does not give Florence a source-compatible Browserbase implementation of it. | Kernel materially shortens the path to a reliable visual fallback. |
| Uploads and downloads | Kernel exposes browser filesystem I/O and supports Playwright/CDP file flows ([File I/O](https://www.kernel.sh/docs/browsers/file-io/)). | Browserbase supports direct Playwright uploads, a Session Uploads API, and persistent download objects ([uploads](https://docs.browserbase.com/platform/browser/files/uploads), [downloads](https://docs.browserbase.com/platform/browser/files/downloads)). | Rough parity at provider level. Port the smallest Kernel file seam required by Florence's real workflows; do not create an abstract filesystem product. |
| Live handoff | Browser creation returns a live-view URL, and sessions can be reconnected; its FAQ says bot-detection behavior is site/configuration-specific and recommends profiles, stealth, and computer controls rather than claiming a fixed supported-site list ([create](https://www.kernel.sh/docs/introduction/create), [FAQ](https://www.kernel.sh/docs/browsers/faq)). | Live View lets a person watch, click, type, and scroll in a running session ([live view](https://docs.browserbase.com/platform/browser/observability/session-live-view)). | Both support handoff. Preserve Florence's current `owner_handoff` behavior and substitute the Kernel live-view URL. |
| Migration cost | Add `@onkernel/sdk`; replace the internals of Florence's browser client; persist/derive a stable profile; add Playwright-program, computer-action, and selected-image operations. OpenInstinct provides the implementation and focused tests. | No provider migration, but Florence would still need to build persistent Context usage, richer Playwright execution, visual actions, and user-visible artifacts itself. | Kernel is the faster route to the desired operator. The meaningful cost is extending Florence's tool contract, not changing session creation. |

### Provider recommendation

Use Kernel as the replacement provider behind the existing `FlorenceBrowserClient` boundary. Keep the current `FamilyWorkStateV1` checkpoint, pending-call identity, effect receipts, owner handoff, steering, cancellation, and “do not replay an uncertain mutation” behavior. Those are Florence's stronger durable semantics and should wrap Kernel just as they currently wrap Browserbase.

During rollout, leave the Browserbase code path available only until a small representative product matrix passes against Kernel: persistent login across runs, a DOM-driven form, a visually driven page, file upload, file download, owner handoff, and a final external action with provider confirmation. Then remove Browserbase. Do not build a generic two-provider router or keep permanent duplicate infrastructure without evidence that a real family workflow needs it.

The implementation should expose one general browser capability to the reasoner, with three composable execution modes:

1. an in-VM Playwright program for efficient DOM inspection/action/verification;
2. native computer actions with screenshots when visual control is the better path; and
3. a selected-image/artifact output when visual evidence materially improves the family-facing result.

This is the same general agent choosing tactics from page state. It is not a catalog of shopping, travel, booking, or school-portal workflows.

## Exact reuse plan

### Port first

- The profile/session lifecycle from [`manage_browsers.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/agent/subagents/worker/tools/manage_browsers.ts), including stable profile identity, target-URL creation, read-only normal sessions, writable auth sessions, stale-record cleanup, and a single profile writer.
- The Kernel call and model-output projection from [`execute_playwright_code.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/agent/subagents/worker/tools/execute_playwright_code.ts), while replacing its exact timeout with Florence's ordinary cancellable call boundary.
- The action vocabulary and contiguous batching from [`computer_action.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/agent/subagents/worker/tools/computer_action.ts).
- The capture modes, original-resource fallback, and idempotent artifact identity from [`capture_browser_image.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/agent/subagents/worker/tools/capture_browser_image.ts), mapped to Florence's storage and Linq delivery.
- The focused provider cases in [`kernel-browser-contract.test.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/tests/kernel-browser-contract.test.ts) and [`worker-browser-tools.test.ts`](https://github.com/Merit-Systems/OpenInstinct/blob/480045dbc63008e7f99313d1683858cd8657b35a/tests/worker-browser-tools.test.ts), rewritten around Florence's interface. These are implementation-adjacent verification, not a new test framework.

### Adapt second

- Native Linq file delivery and natural message-bubble grouping.
- Persistent account setup through Kernel profiles first; Managed Auth or opaque form autofill only when a real repeat-login workflow needs more.
- A small amount of OpenInstinct's conversational language about deriving details, changing tactics, taking the next reversible step, and giving a concise verified result.

### Do not take

- Eve, Vercel task history, Next.js, Neon, Blob, Better Auth, or the root/worker runtime split.
- Per-person file memory as a replacement for Florence's household Vault.
- OpenInstinct's Google adapter or any of its fixed result slices.
- Its 90-second, six-call, two-tactic, 25-second, or 20-action numbers as limits on completing an objective.
- The automatic thumbs-up emitted whenever the model starts tool calls.
- The public browser benchmark as sufficient product validation; its simple public-page tasks do not cover persistent family accounts, owner handoff, long-running continuation, or consequential external actions.

## Top three product changes this should cause

1. **Replace Browserbase with a Kernel-backed deep browser operator inside Florence's existing durable loop.** Port persistent profiles, in-VM Playwright, and native computer actions rather than recreating them. This is the largest direct capability gain and makes arbitrary sites a practical continuation of the general agent instead of a brittle sequence of accessibility references.
2. **Let Florence deliver the visual result, not just describe that browser work happened.** Port selected browser-image artifacts and native Linq attachment delivery so dinner options, products, listings, seating, and useful confirmation evidence can appear naturally in the family thread.
3. **Make browser identity persist across work.** Use stable adult/household Kernel profiles and deliberate login-state writes so a parent signs in once and Florence can keep working later. Evaluate Managed Auth or opaque autofill after this base works; do not turn Florence's household-knowledge Vault into a credentials product.

OpenInstinct does not change Florence's product destination. It supplies a strong, reusable execution layer for one important part of it.
