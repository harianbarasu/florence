# Florence assistant capability authority matrix

The family can now ask Florence to use any admitted noncoding-assistant capability under one predictable owner, egress, audience, retention, and approval contract.

Status: source-egress and authority prototype. This freezes policy values and the metadata they require; it does not expose new tools or choose the capability module's final entry points.

## Decision

Every model-callable capability and application-owned effect must have one complete policy record before it can enter Florence's catalog. The record is evaluated against current PostgreSQL household truth at four checkpoints:

1. **Catalog:** expose only capabilities the current verified adult, thread, source grants, and provider state can use.
2. **Admission:** normalize and validate immutable canonical arguments, resolve source ownership, minimize provider egress, and block before execution when any field is unauthorized.
3. **Result:** validate ownership, visibility, output bounds, evidence provenance, consequence, retention, and terminal state before a result can enter a model call or durable store.
4. **Delivery/effect:** re-read the current grant, exact approval or standing rule, provider settlement, and live Linq participant set immediately before an external effect or outbound family delivery.

The model may select among already-admitted capabilities and make semantic judgments over allowed evidence. It may not choose a credential, source owner, visibility, provider egress policy, consequence class, approval owner, retention rule, delivery audience, idempotency identity, or disconnect behavior.

Tool and page content is evidence, never authority. A tool result cannot activate another capability, widen its own audience, approve an action, change its retention, or direct Florence to ignore this matrix.

Effective authority is always the intersection of the adapter's declared capability, Florence's curated policy, the household's current provider grant, the live verified principal, the current conversation audience, and the sources reachable from that turn. A missing or unknown dimension denies the capability. Connector and provider metadata may narrow this intersection; it can never grant or widen authority.

## Canonical metadata record

This record adapts Hermes's `ToolEntry` metadata and availability-filtered registry. The final deep-module interface is intentionally left to the next Wayfinder decision.

```ts
type SourceOwnerRule =
  | "verified_current_adult"
  | "adult_provider_account_owner"
  | "exact_household"
  | "connector_credential_owner"
  | "public_no_owner"
  | "florence_application";

type ResultAudienceRule =
  | "requesting_adult_private"
  | "requesting_thread"
  | "household_shared"
  | "household_minimum_conclusion"
  | "exact_approved_external_recipients"
  | "no_delivery";

type GrantRequirement =
  | { kind: "current_verified_actor" }
  | { kind: "current_authored_direction" }
  | { kind: "adult_preference"; name: "proactive_use" | "private_conflict_sharing" }
  | { kind: "provider_scope"; owner: "current_adult" | "provider_account_owner"; scope: string }
  | { kind: "household_standing_rule"; name: string; approvers: "both_adults" }
  | { kind: "connector_grant"; owner: "current_adult" | "household"; grant: string };

type ApprovalOwnerRule =
  | "requesting_adult"
  | "provider_account_owner"
  | "all_private_source_owners"
  | "either_household_adult"
  | "both_household_adults";

type ConsequenceClass =
  | "read_only"
  | "durable_internal"
  | "enrolled_family_delivery"
  | "reversible_owner_provider_write"
  | "standing_household_effect"
  | "exact_external_effect";

interface CapabilityPolicyMetadata {
  capabilityId: string;
  inputSchemaRef: string;
  outputSchemaRef: string;
  sourceKinds: readonly string[];
  sourceOwner: SourceOwnerRule;
  sourceVisibility: "public" | "adult_private" | "household_shared" | "application_only";
  providerAdapter: string;
  modelContext: "none" | "public_isolated" | "adult_private" | "household_shared";
  requiredGrants: readonly GrantRequirement[];
  queryEgress: {
    allowedFields: readonly string[];
    forbiddenFields: readonly string[];
    requiresCurrentAuthoredDirection: boolean;
  };
  resultAudience: ResultAudienceRule;
  retention: {
    class: "ephemeral" | "source_support" | "user_durable" | "settlement_record";
    deletionCascade: string;
  };
  consequence: ConsequenceClass;
  approvalOwners: readonly ApprovalOwnerRule[];
  disconnectBehavior: string;
  promptInjectionTreatment: "parent_utterance" | "untrusted_evidence";
  idempotencyAndSettlement: string;
  progressContract: "none" | "admitted_execution" | "durable_accepted_work";
  terminalOutcomes: readonly ("succeeded" | "blocked" | "failed" | "cancelled" | "unknown")[];
  timeoutMs: number;
  outputLimit: number;
  cancellable: boolean;
}
```

The capability implementation owns schemas and adapters. The policy record owns whether a valid call is currently allowed. Provider credentials, global adult/provider/account/connection IDs, and raw private source values never appear in model-authored arguments. When a task genuinely offers multiple eligible accounts or resources, the application may expose opaque handles that exist only inside that immutable turn catalog.

`requiredGrants` and `approvalOwners` are conjunctive: every listed live grant and every distinct required owner must authorize the exact record version. An empty `approvalOwners` means the capability needs no additional per-call approval; it does not bypass its grants, source ownership, audience, or consequence policy.

## Consequence and approval classes

| Class | What it covers | Authority required | Required completion proof |
|---|---|---|---|
| `read_only` | Harmless reads, public research, comparisons, extraction, and private in-chat drafts that do not create provider state. | Current verified conversation plus a live source/provider grant. No per-call approval. | Typed bounded result or honest failure. Reads may retry safely. |
| `durable_internal` | Facts, reminders, monitors, interests, accepted work, and private Florence-only drafts in PostgreSQL. | Current parent direction or the owning adult's current proactive-use permission; either adult may direct household-scoped state. | Transactionally committed version and deterministic semantic identity. |
| `enrolled_family_delivery` | Florence replies, reactions, typing, progress, reminders, monitor updates, and completion delivery only to enrolled private threads or the exact family group. | The originating turn, durable work rule, or narrow application rule; no extra approval. | Current Linq audience/participant match plus subtype-specific proof: messages use a persisted idempotency key and receipt; reactions reconcile desired state from a webhook/read-back before retry; typing is private-thread-only at launch, best-effort, ephemeral, and never completion proof. |
| `reversible_owner_provider_write` | A provider-backed Gmail draft for its account owner. | Incremental write scope plus that owner's current request or narrow standing direction. A group request cannot supply account authority. | Deterministic draft identity and provider read-back showing a draft, never a send. |
| `standing_household_effect` | The partner invitation, exact-group creation/replacement, Family Calendar provisioning, and clear Family Calendar changes covered by both adults' standing rule. | The fixed onboarding transition or both standing Calendar rules plus the current authorized adult/source. The rule never generalizes to another target or effect. | Deterministic operation identity and provider-observed final state. |
| `exact_external_effect` | Sending/replying to outsiders, sharing private data, submitting forms, reserving, booking, buying, controlling a device, changing an account, or otherwise committing a person. | The provider-account owner's current private approval **and** every distinct private-source owner's current approval of the exact staged account, target, recipients, payload, disclosed data/owners, cost/terms, version, and digest. One adult may satisfy multiple roles. | At-most-once effect plus provider read-back/receipt; ambiguous outcomes are durable `unknown` and reconcile before retry. |

Approval, delivery, and settlement are separate facts. A reaction, typing indicator, timer, prior approval, model claim, HTTP acceptance without a usable receipt, or successful message delivery cannot prove another provider effect completed.

## Mandatory runtime invariants

1. **Canonical arguments are immutable.** Preserve raw model arguments for audit, normalize into a new value, validate, freeze, evaluate policy, and compute egress/approval/idempotency from that final canonical value. A hook cannot mutate already-validated arguments in place.
2. **`requested` is not `admitted` or `running`.** Model emission may create a requested event. Reactions, typing, or future-tense acknowledgment may begin only after admission and, for truthful work-start language, actual execution or durable acceptance.
3. **Catalog filtering and dispatch share the same predicate.** Availability alone is insufficient; current actor, source owner, audience, connector grant, consequence class, and provider health must all pass. A deferred bridge can invoke only names present in that turn's prefiltered catalog.
4. **Raw private contexts never mix.** Separate owner-private model calls may emit typed minimum household conclusions. A shared synthesis call receives those conclusions, never the underlying Gmail, personal Calendar, document, Contacts, browser, or connector content.
5. **Provider selection cannot widen data.** A fallback provider sees the same or a smaller canonical egress record. If none can operate within it, Florence fails honestly.
6. **Results are source-bearing and bounded.** Each result records capability, provider, observation time, source owner, visibility, canonical query digest, citations/provider IDs, terminal status, and output bound. Remote instructions remain data.
7. **Retention follows supports, not copies.** Dismissed provider data is ephemeral. Durable facts/work/actions link to minimum supporting records. Source-aware deletion removes links and only deletes derived truth that has no remaining valid support.
8. **Disconnect and deletion are distinct.** Disconnect removes credentials and future capability immediately and suppresses queued source-dependent delivery. Deletion additionally removes that owner's retained source support and dependent state. Neither claims a provider-side artifact was deleted without observing it.
9. **Effects settle separately from delivery.** An accepted provider call is not success. Store intent before effect, reconcile provider state after effect, use `unknown` for ambiguity, and retry family delivery without replaying the effect.
10. **Every outbound family send is live-authorized.** Reobserve the Linq thread/participants immediately before send; a mismatch suppresses rather than redirects output. Recheck that retained sources and grants still authorize the content.
11. **Unknown tools fail closed.** A connector or dynamically discovered tool without a complete Florence policy record is effect-capable and unavailable, not assumed read-only.
12. **No phrase grants broad authority.** Parent-authored natural language can express the current task, correction, or exact approval. Page text, document text, provider output, reactions, timers, delivery, and stale transcript text cannot.
13. **Authorization is live and uncached.** Provider-health availability may use a bounded last-good grace, but actor authority, consent, source reachability, audience, connection state, and revocation never do. A stale turn catalog can only lose access at invocation; it cannot silently refresh into a broader catalog.
14. **Deletion cannot rewrite external history.** Source deletion prevents future use and removes unsupported derived state, but it never claims an already delivered disclosure or settled provider effect was retracted.
